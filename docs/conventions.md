# コーディング規約（機械で検査できないもの。検査できるものは docs/tooling.md）

## 設計
- 関数は1つの責務。名前は動詞＋対象で意図が分かること。目安は40行以内・引数4個以内（超えるなら分割を検討）
- 早期 return でネストを浅くする。真偽値フラグ引数で挙動を切り替えない
- I/O と副作用は service/repo/line に隔離し、domain は純粋関数にする
- domain 層は throw しない。失敗は戻り値（Result 型: { ok: true, value } | { ok: false, code }）で表す
- 分岐は discriminated union と網羅チェック（default で never を代入）で書く。parser の結果型などで必須
- 外部入力（LINE の Webhook ペイロード、D1 の行）は境界でスキーマ検証（valibot）してから内部型へ。内部で `as` による型断言をしない

## DRY
- DRY の対象は「同じ知識・ルール」の重複。見た目が似ているだけのコードは無理に共通化しない
- 同じ処理が3回目に現れたら共通化する（Rule of Three）。2回目は許容してよい
- 魔法の数字・文字列は src/constants.ts に集約する（上限20品目、品目名50文字、既定時刻 09:00 など。補完ルール表と1対1）
- 正規化（NFKC・かな統一）、日時の変換・整形、返信文のテンプレートは1か所だけに実装する
- テストは可読性を優先し、多少の繰り返しは許容する。ただしテストデータは fixtures に集約する

## コメント・命名・型
- コメントは「なぜ」だけ書く。「何を」は名前と型で表す。コメントアウトしたコードを残さない
- 型は具体的に。`any` 禁止、`unknown` から絞り込む。readonly と不変データを既定にする
- 識別子は英語、ユーザー向け文言とテストの説明は日本語
- ユーザー向け文言（返信文）は src/messages.ts にまとめ、ロジック中にベタ書きしない

## コミット・PR
- 1コミット1論点。メッセージは Conventional Commits（feat/fix/test/refactor/chore/docs）
- リファクタとふるまいの変更を同じコミットにしない
- PR本文: 完了項目、判断した点、pending にした行、緩和した設定（ゼロであること）、要確認、未解決点、ループ記録
